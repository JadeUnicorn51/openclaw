# 建筑行业采购 AI 助手开发计划 v1.1

## 一、可行性结论

结论：**可行，但需要按 MVP 优先、分阶段落地**。

基于 openclaw 二次开发这条路线成立，原因如下：

- `ui/`、`Lit + Vite`、现有模型配置、技能加载、部分知识库能力可以复用。
- 桌面壳可以通过 Electron 新增，不需要重写前端。
- 本地数据存储可以继续采用 `SQLite + sqlite-vec`。
- 行业角色、提示词、工作流和知识库组织方式属于产品层能力，适合在现有能力上叠加。

但原始计划里有几项判断过于乐观：

- 不能把现有 UI 到 Gateway 的通信简单理解为“HTTP 可替代 WebSocket”。
- 不能把现有 `workspace` 直接等同为“带成员和权限的业务工作区”。
- 不能把“PDF、Excel、章节、表格、整文”统一视为只增加几种 chunk 策略。
- 不能把“全本地优先”和“默认使用远程 OpenAI 兼容模型”同时表述成“无外部依赖”。

因此，v1.1 版本采用以下原则：

- **先做单机 MVP，再做协作和商业化。**
- **先复用现有 Gateway WebSocket 通信，再决定是否补 REST。**
- **先做单用户工作区隔离，再做多成员权限。**
- **先做文本型文档入库，再做表格保真、扫描件 OCR 和复杂解析。**

## 二、产品定位

**产品名称**：建筑行业采购 AI 助手（暂定名 PurchaseAI）

**目标用户**：

- 建筑行业采购员
- 造价员
- 资料员
- 招投标专员
- 项目经理

**核心价值**：

- 桌面端交付，优先支持 Windows，后续支持 macOS。
- 数据本地存储，本地优先运行。
- 围绕建筑采购和项目资料场景提供预置角色和知识库能力。
- 支持工作区隔离，后续支持局域网协作和商业化授权。

**产品口径修正**：

- “全本地优先”指的是应用、配置、知识库和向量索引本地落盘。
- 模型推理和 embedding 可以接本地模型，也可以接远程 OpenAI 兼容接口。
- 在未接入本地模型前，不应对外宣传为“完全离线、无外部依赖”。

## 三、范围划分

### 3.1 MVP 范围

MVP 只覆盖以下能力：

- Electron 桌面壳
- 单用户工作区
- 本地知识库导入与查询
- 基础文档分块策略
- 建筑行业预置角色
- 模型配置中心

### 3.2 MVP 明确不做

以下能力不进入首发范围：

- 多成员协作
- 局域网共享
- 证书激活和授权分层
- 插件售卖系统
- 自定义技能编辑器
- 扫描版 PDF OCR
- Excel 表格结构高保真抽取

### 3.3 MVP 后续范围

MVP 稳定后按优先级追加：

1. 证书激活与商业化限制
2. 多工作区多成员权限
3. 局域网共享
4. 文档解析增强
5. 插件售卖和技能编辑器

## 四、技术路线

### 4.1 技术栈

| 层级 | 技术 | 说明 |
|------|------|------|
| 前端 UI | Lit 3.3.2 + Vite | 复用 `ui/` |
| 桌面壳 | Electron | 新增 |
| 后端运行时 | Node.js + TypeScript | 复用 openclaw 核心 |
| 通信层 | Gateway WebSocket | MVP 保持现有协议 |
| 本地存储 | SQLite | 配置、索引、业务数据 |
| 向量检索 | sqlite-vec | 轻量默认方案 |
| 大规模向量库 | LanceDB | 后续按容量需要启用 |
| 模型接入 | OpenAI 兼容接口 + 本地模型适配 | 复用现有配置体系 |
| 技能系统 | Skills | 复用现有 `skills/` |

### 4.2 复用判断

| 模块 | 复用判断 | 说明 |
|------|----------|------|
| `ui/` | 高 | 可以直接复用大部分前端代码 |
| Gateway 协议与连接层 | 高 | 应保持现有 WebSocket 模型 |
| `memory-host-sdk` 文本分块与索引 | 中 | 可复用基础能力，但需补文档解析层 |
| 模型配置与 provider 配置 | 高 | 可直接沿用 |
| 技能系统 | 中 | 可复用加载能力，但工作区级技能管理仍需产品层实现 |
| 插件系统 | 中 | 可用作扩展基础设施，不建议首发即做售卖 |
| 业务工作区与成员权限 | 低 | 基本属于新增产品层能力 |
| 授权激活 | 低 | 基本属于新增业务能力 |

### 4.3 复用率估算

- **MVP 复用率**：约 50-60%
- **完整产品复用率**：约 35-50%

原因：

- UI 和模型接入可以大量复用。
- 业务工作区、成员权限、授权激活、协作模式都需要新建。
- 文档解析成本高于分块策略本身。

## 五、核心架构决策

### 5.1 桌面端策略

MVP 采用 Electron 作为桌面壳，目标是先交付 Windows 版本。

原因：

- 可以较低成本复用现有 `ui/`。
- 对产品验证速度更友好。
- Windows 是采购办公场景的主要平台。

macOS 策略单列为决策项：

- 方案 A：继续沿用仓库现有原生容器思路。
- 方案 B：统一转向 Electron。

该决策不应阻塞 MVP Windows 版本。

### 5.2 通信层策略

MVP **不新增 REST 替换层**，继续沿用现有 Gateway WebSocket 模型。

原因：

- 现有 UI 已依赖 Gateway WebSocket 连接和握手。
- 若改为 REST，需要同时改动前端状态同步、事件推送和会话控制。
- 这会显著扩大首发范围。

后续如果有局域网协作或外部集成需求，再在现有协议之上补充 API，而不是先重写通信模型。

### 5.3 工作区策略

MVP 的“工作区”定义如下：

- 单用户可创建多个本地工作区。
- 每个工作区有独立配置、知识库、角色设置和技能目录。
- 不包含成员、RBAC、共享协作。

后续版本再引入：

- 成员管理
- 权限矩阵
- 共享工作区
- 局域网协作

### 5.4 知识库策略

知识库能力拆成两层：

- **文档解析层**：负责提取文本、章节、表格和元数据。
- **分块策略层**：负责如何切 chunk 和如何入向量库。

MVP 只保证以下输入稳定可用：

- `txt`
- `md`
- `json`
- 带文本层的 `pdf`

后续增强：

- `docx`
- `xlsx`
- 扫描 PDF OCR
- 表格结构高保真抽取

## 六、功能设计

### 6.1 Electron 桌面端

**目标**：封装现有 Lit UI，提供桌面窗口、菜单、托盘和安全 IPC。

**实现要点**：

- 使用 `BrowserWindow` 承载 `ui/` 构建产物。
- 使用 `preload + contextBridge` 暴露受控 API。
- 支持自定义协议和本地资源访问。
- 补充窗口管理、系统菜单、托盘和启动参数。

**建议目录**：

```text
electron/
├── src/
│   ├── main/
│   │   ├── index.ts
│   │   ├── window.ts
│   │   ├── protocol.ts
│   │   ├── ipc-handlers.ts
│   │   ├── menu.ts
│   │   └── tray.ts
│   └── preload/
│       └── index.ts
├── package.json
└── tsconfig.json
```

**验收标准**：

- [ ] Electron 应用可启动
- [ ] `ui/` 页面可加载
- [ ] Gateway 连接可建立
- [ ] 窗口与托盘行为正常

### 6.2 单用户工作区

**目标**：支持多个完全隔离的本地工作区。

**目录建议**：

```text
~/.purchase-ai/
├── config.json
├── state.db
└── workspaces/
    └── {workspaceId}/
        ├── config.json
        ├── knowledge.db
        ├── files/
        ├── chunks/
        ├── agents/
        └── skills/
```

MVP 不单独引入 `members.db`，统一先收敛到单用户模型，避免过早设计多成员 schema。

**验收标准**：

- [ ] 创建、切换、删除工作区正常
- [ ] 工作区配置互不影响
- [ ] 知识库和文件数据完全隔离

### 6.3 知识库导入与分块

**MVP 支持的策略**：

| 策略 | 场景 | 说明 |
|------|------|------|
| `tokens` | 通用文本 | 默认策略 |
| `paragraphs` | 普通文档 | 按段落切分 |
| `section` | 规范文本 | 基于标题或显式章节切分 |
| `whole_doc` | 短合同或短制度文档 | 整文入库，需设置大小上限 |

MVP 暂不承诺 `table` 策略，因为它依赖更稳定的表格解析层。

**关键实现点**：

- 保持 `packages/memory-host-sdk/src/host/internal.ts` 的基础文本分块能力。
- 新增解析层与策略工厂，不直接把所有新逻辑塞回 `chunkMarkdown`。
- 为整文模式设置输入大小门槛，避免 embedding 上限问题。

**验收标准**：

- [ ] 文本文档可导入和查询
- [ ] 文本层 PDF 可导入和查询
- [ ] `tokens`、`paragraphs`、`section`、`whole_doc` 可单独验证
- [ ] 不同策略互不干扰

### 6.4 建筑行业预置角色

**首发角色**：

| ID | 名称 | 核心能力 |
|----|------|---------|
| `purchaser` | 采购员 | 供应商评估、询价、比价、合同审查 |
| `cost_engineer` | 造价员 | 清单编制、预算审核、变更测算 |
| `archivist` | 资料员 | 文档整理、归档、检索 |
| `bidding` | 招投标专员 | 标书编制、资格预审、开标分析 |
| `project_manager` | 项目经理 | 进度跟踪、风险识别、资源协调 |

**角色模型建议**：

```ts
interface AgentRole {
  id: string;
  name: string;
  description: string;
  systemPrompt: string;
  skills: string[];
  allowedKnowledgeScopes?: string[];
}
```

MVP 不把角色权限和商业授权绑死在一起，先只做产品能力分层。

**验收标准**：

- [ ] 角色可切换
- [ ] 角色提示词和技能集生效
- [ ] 不同角色在同一知识库上的回答风格可区分

### 6.5 模型配置中心

**目标**：支持全局配置和工作区覆盖。

**规则**：

- 全局配置作为默认值。
- 工作区可以覆盖对话模型和 embedding 模型。
- 模型配置保留现有 OpenAI 兼容 provider 接入方式。
- 若启用本地模型，产品层只负责配置和健康检查，不重新发明模型接入协议。

**验收标准**：

- [ ] 全局配置可保存
- [ ] 工作区覆盖配置可生效
- [ ] 模型切换后查询和对话正常

## 七、后续版本设计

### 7.1 授权激活系统

授权激活不进入 MVP，但可以提前定义边界。

**建议原则**：

- 激活逻辑放在产品层，不侵入核心推理链路。
- 限制项以“功能开关”和“额度限制”为主。
- 机器码只作为授权绑定依据，不应成为核心数据访问前提。

**建议限制项**：

- 工作区数量
- 高级分块策略
- 自定义技能
- 局域网共享
- 角色数量上限

### 7.2 多成员工作区

该阶段才引入：

- `members`
- `roles`
- `permissions`
- 成员邀请和退出
- 审计日志

没有审计和冲突策略前，不建议直接上线共享编辑。

### 7.3 局域网共享

局域网共享基于“主机节点 + 成员客户端”模式。

建议路线：

- 复用现有 Gateway 和认证思路。
- 补充主机发现、配对、权限同步。
- 尽量保持协议增量演进，避免平行维护一套 REST 和一套 WebSocket。

## 八、安装包产品化方案

### 8.1 目标形态

本项目首发不是“要求用户先安装 npm 版 openclaw 再做配置”，而是：

- 直接提供可安装的桌面安装包
- 安装后可直接启动
- 首次启动通过产品内引导完成基础配置
- 常用能力通过 UI 暴露
- 高级能力保留配置文件和开发者入口

对外产品形态应为：

- Windows：优先交付 `.exe` 安装包
- macOS：后续补齐 `.dmg` 或 `.app` 分发

### 8.2 安装包应包含的内容

安装包内应直接包含以下组成部分：

- 应用前端构建产物
- Electron 主进程和 preload
- openclaw 运行时代码
- Node 运行时
- 生产依赖
- 默认资源和内置角色模板

这意味着用户不需要手工执行：

- `npm install -g openclaw`
- `openclaw onboard`
- `openclaw config set ...`

这些动作要被替换为应用内流程。

### 8.3 首次启动流程

首次启动建议采用“引导式初始化”：

1. 选择工作区目录或使用默认目录
2. 选择模型接入方式
3. 配置默认对话模型和 embedding 模型
4. 初始化 Gateway 本地运行模式
5. 创建默认工作区
6. 生成默认行业角色与基础设置
7. 进入主界面

若用户跳过部分设置，则应用应：

- 写入最小可运行默认配置
- 标记相关能力为“未完成配置”
- 在设置页中继续补完

### 8.4 CLI 能力的产品化处理

当前通过命令行完成的主要能力，需要映射到安装包版本的产品能力：

| 当前方式 | 安装包版本对应形态 |
|------|------|
| `openclaw onboard` | 首次启动向导 |
| `openclaw configure` | 设置页 / 配置向导 |
| `openclaw config set/get` | 设置页 + 高级配置页 |
| 直接编辑配置文件 | 开发者模式 / 高级配置入口 |
| 手工启动 gateway | 应用后台自动托管 |

原则如下：

- 常用配置必须可视化。
- 不常用高级配置可以继续落在配置文件。
- 不为了“去 CLI”而删除高级能力，只是把它们降级为高级入口。

### 8.5 MVP 安装包边界

MVP 安装包必须满足以下条件：

- 安装后无需额外安装 Node 或 npm
- 应用可独立启动
- 首次启动可完成基础模型配置
- 可创建工作区、导入文档、切换角色
- 不依赖用户手工执行命令行初始化

MVP 安装包暂不要求：

- 覆盖全部 CLI 子命令
- 提供完整开发者工具面板
- 提供一键导入复杂多 profile 环境
- 提供局域网共享配置向导

## 十一、执行方式

默认执行方式如下：

- 产品方案、架构改造、代码实现、联调、验证和文档更新都由 Codex 推进完成。
- 用户主要负责业务确认、优先级确认和阶段验收。
- 除非涉及产品方向冲突、高风险取舍或外部资源缺失，否则不把实现工作回退给用户。

执行原则：

- 优先直接修改代码和文档，不只给建议。
- 每个阶段都要给出可运行结果或明确阻塞。
- 遇到大范围目标时，按阶段持续推进，不要求用户手工拆任务。
- 如需用户决策，只在确实存在多种高影响方案时再确认。

对当前项目的含义是：

- “做成安装包”
  指由我负责把当前核心能力整理为桌面产品交付形态。
- “实现当前功能”
  指由我负责把现有 openclaw 可复用能力接入桌面端，而不是要求用户继续用命令行手工拼装。

## 十二、主要风险与缓解措施

### 12.1 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| UI 与 Gateway 耦合较深 | 高 | MVP 保持现有 WebSocket 模型，不先改 REST |
| Electron 双平台兼容性 | 中 | 先交付 Windows，macOS 单列决策 |
| 文档解析复杂度被低估 | 高 | 分离解析层和分块层，先支持文本型文档 |
| `memory-host-sdk` 改动点分散 | 中 | 先确认源码主入口和边界，再实施改造 |
| 向量检索规模增长后性能下降 | 中 | MVP 使用 sqlite-vec，大规模场景再评估 LanceDB |

### 12.2 产品风险

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| “全本地”宣传与真实依赖不一致 | 高 | 明确区分本地数据和模型运行模式 |
| 角色设计过泛，行业价值不明显 | 中 | 用真实采购、造价、招投标样本迭代提示词 |
| 首发范围过大导致延期 | 高 | 坚持 MVP 边界，不提前引入协作和授权 |

## 十三、验证与发布 gate

每个 Phase 完成后至少通过以下检查：

1. `pnpm build`
2. `pnpm check`
3. 对应的 scoped test 或最直接的手动验证
4. 桌面端启动无阻断性错误

MVP 发布前建议至少通过：

1. Windows 安装包可正常安装和启动
2. 工作区创建、切换、删除完整走通
3. 文档导入、索引、检索和问答完整走通
4. 5 个行业角色可切换
5. 默认模型配置和工作区覆盖配置可生效
